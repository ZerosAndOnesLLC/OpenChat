# OpenChat V2: WebSocket-First Architecture

## Problem Statement

### Current Architecture Issues

The current OpenChat implementation has a fundamental architectural flaw that prevents it from scaling efficiently:

**When a user clicks on a channel:**
1. UI makes 4-6+ parallel HTTP requests:
   - `GET /api/channels/{id}/unread` - Unread count & last read message
   - `GET /api/channels/{id}/messages` - Message history
   - `GET /api/channels/{id}/pins` - Pinned messages
   - `GET /api/bookmarks` - User bookmarks
   - Additional requests for reactions, threads, etc.

2. **Each HTTP request triggers:**
   - Token verification call to TitaniumVault API
   - Database connection from pool
   - RLS (Row Level Security) context setup
   - Database queries
   - Redis cache lookups

3. **Result:** Opening a single channel = **10-15 external API calls** to TitaniumVault

### Evidence from Logs

```
2025-11-20T18:36:00.723 - Starting new connection to TitaniumVault
2025-11-20T18:36:00.883 - Starting new connection to TitaniumVault
2025-11-20T18:36:01.043 - Starting new connection to TitaniumVault
2025-11-20T18:36:01.208 - Starting new connection to TitaniumVault
2025-11-20T18:36:01.356 - Starting new connection to TitaniumVault
... (continues 10+ times)
```

### Why This Doesn't Scale

- **TitaniumVault Bottleneck:** Every request validates token with external service
- **Connection Overhead:** Each HTTP request = new TLS handshake, auth, DB connection
- **Latency Multiplication:** 10 requests × 50ms = 500ms+ just for auth
- **Resource Waste:** Repeated token verification for same user within seconds
- **Poor UX:** Slow channel switching, loading indicators, perceived lag

## How Industry Leaders Do It

### Slack's Architecture

1. **Initial WebSocket Connection:**
   ```json
   {
     "type": "hello",
     "connection_info": {...},
     "self": {...user...},
     "teams": [...],
     "channels": [...],  // All channels with metadata
     "ims": [...],       // All DMs with metadata
     "users": [...]      // Team members
   }
   ```

2. **Channel Switch:**
   ```
   Client: { "type": "subscribe", "channel": "C123" }
   Server: {
     "type": "channel_joined",
     "channel": {...},
     "messages": [...last 50...],
     "pins": [...],
     "members": [...]
   }
   ```

3. **All Updates via WebSocket:**
   - New messages pushed in real-time
   - Typing indicators
   - Presence updates
   - Unread count changes
   - Pin/unpin events
   - **Zero HTTP calls during normal operation**

### Mattermost's Architecture

Similar WebSocket-first approach:
- Initial state loaded via WebSocket on connect
- Channel data sent when switching channels
- Real-time updates for everything
- HTTP API used only for:
  - File uploads
  - Search (complex queries)
  - Admin operations
  - Initial authentication

### Discord's Architecture

Even more aggressive:
- Gateway WebSocket connection handles all real-time data
- HTTP API exists but is rate-limited
- Encourages WebSocket for all operations
- Efficient binary protocol (optional)

#### 1.2 Channel Subscription Enhancement

When client subscribes to channel, send all needed data:

pub enum ServerMessage {
    ChannelData {
        channel_id: Uuid,

        members: Vec<ChannelMember>,
        unread_info: UnreadInfo,

**Implementation:**
```rust
impl Handler<SubscribeChannel> for WsServer {
    fn handle(&mut self, msg: SubscribeChannel, ctx: &mut Context<Self>) {
        // Register subscription (existing)
        self.channel_subscriptions
            .entry(msg.channel_id)
            .or_insert_with(HashSet::new)
            .insert(msg.session_id);

        // NEW: Fetch and send channel data
        let pool = self.pool.clone();
        let session = self.sessions.get(&msg.session_id).cloned();

        ctx.spawn(
            async move {
                // Fetch all data in parallel
                let (messages, pins, members, unread) = tokio::join!(
                    Message::list_for_channel(&pool, msg.channel_id, 50),
                    PinnedMessage::list_for_channel(&pool, msg.channel_id),
                    ChannelMember::list_for_channel(&pool, msg.channel_id),
                    get_unread_info(&pool, msg.user_id, msg.channel_id)
                );

                // Send to client
                if let Some(session) = session {
                    session.do_send(ServerMessage::ChannelData {
                        channel_id: msg.channel_id,
                        messages: messages.unwrap_or_default(),
                        pins: pins.unwrap_or_default(),
                        members: members.unwrap_or_default(),
                        unread_info: unread.unwrap_or_default(),
                    });
                }
            }
            .into_actor(self)
        );
    }
}
```

### Phase 3: Token Caching (Interim Solution)

While implementing full WebSocket architecture, add token caching as immediate optimization:

#### 3.1 Token Claims Cache

```rust
// cache/tokens.rs
pub async fn get_cached_token_claims(
    redis: &mut MultiplexedConnection,
    token: &str,
) -> ApiResult<Option<TokenClaims>> {
    let hash = sha256::digest(token);
    let key = format!("openchat:token:{}", hash);

    if let Ok(Some(cached)) = redis::cmd("GET")
        .arg(&key)
        .query_async::<_, Option<String>>(redis)
        .await
    {
        if let Ok(claims) = serde_json::from_str(&cached) {
            return Ok(Some(claims));
        }
    }

    Ok(None)
}

pub async fn cache_token_claims(
    redis: &mut MultiplexedConnection,
    token: &str,
    claims: &TokenClaims,
    ttl_seconds: u64,
) -> ApiResult<()> {
    let hash = sha256::digest(token);
    let key = format!("openchat:token:{}", hash);
    let value = serde_json::to_string(claims)?;

    redis::cmd("SETEX")
        .arg(&key)
        .arg(ttl_seconds)
        .arg(value)
        .query_async(redis)
        .await?;

    Ok(())
}
```

#### 3.2 JWKS Caching

```rust
// services/tv_api.rs
use std::sync::Arc;
use tokio::sync::RwLock;

pub struct TvApiClient {
    base_url: String,
    jwks_cache: Arc<RwLock<Option<(Jwks, Instant)>>>,
    jwks_ttl: Duration,
}

impl TvApiClient {
    pub async fn verify_token(&self, token: &str) -> ApiResult<TokenClaims> {
        // Check JWKS cache first
        let jwks = {
            let cache = self.jwks_cache.read().await;
            if let Some((jwks, cached_at)) = cache.as_ref() {
                if cached_at.elapsed() < self.jwks_ttl {
                    Some(jwks.clone())
                } else {
                    None
                }
            } else {
                None
            }
        };

        let jwks = match jwks {
            Some(jwks) => jwks,
            None => {
                // Fetch and cache JWKS
                let jwks = self.fetch_jwks().await?;
                let mut cache = self.jwks_cache.write().await;
                *cache = Some((jwks.clone(), Instant::now()));
                jwks
            }
        };

        // Verify token with cached JWKS
        self.verify_with_jwks(token, &jwks).await
    }
}
```

#### 3.3 Enhanced Auth Middleware

```rust
impl<S, B> Service<ServiceRequest> for AuthMiddlewareService<S> {
    fn call(&self, req: ServiceRequest) -> Self::Future {
        Box::pin(async move {
            let token = extract_token(&req)?;
            let redis_conn = get_redis(&req)?;
            let mut redis = redis_conn.as_ref().clone();

            // Try cache first
            let claims = match get_cached_token_claims(&mut redis, &token).await? {
                Some(claims) => {
                    debug!("Token cache hit");
                    claims
                }

                    debug!("Token cache miss, verifying with TitaniumVault");
                    let claims = tv_api_client.verify_token(&token).await?;

                    // Cache for 5 minutes

                    claims
                }
            };

            // ... rest of middleware
        })
    }
}
```

- First request: Calls TitaniumVault (cache miss)

- Reduces TitaniumVault calls by ~95%

## Technical Debt & Risks

### Risks

1. **WebSocket Connection Limits**
   - **Risk:** Server can't handle many concurrent connections
   - **Mitigation:** Load balancing, connection pooling, Redis scaling
   - **Monitoring:** Alert on >80% connection capacity

2. **Message Delivery Guarantees**
   - **Risk:** Messages lost during reconnection
   - **Mitigation:** Message sequence numbers, gap detection, replay
   - **Monitoring:** Track message delivery failures

3. **State Synchronization**
   - **Risk:** Client state diverges from server
   - **Mitigation:** Periodic state reconciliation, checksums
   - **Monitoring:** Track state mismatch errors

4. **Migration Complexity**
   - **Risk:** Breaking changes for mobile apps
   - **Mitigation:** Maintain HTTP API compatibility, version headers
   - **Monitoring:** Track deprecated API usage

### Technical Debt to Address

- [ ] Token expiration handling (what happens when cached token expires?)
- [ ] WebSocket reconnection logic (exponential backoff, max retries)
- [ ] Offline queue (messages sent while disconnected)
- [ ] Binary protocol option (more efficient than JSON)
- [ ] Message compression (gzip, brotli)
- [ ] Rate limiting per WebSocket connection
- [ ] Horizontal scaling (Redis pub/sub already implemented)

## Alternative Approaches Considered

### 1. Better HTTP Caching
**Approach:** Use ETags, aggressive caching headers
**Pros:** Easy to implement, works with CDN
**Cons:** Still requires HTTP roundtrips, doesn't solve TitaniumVault issue
**Decision:** Rejected - doesn't address root cause

### 2. GraphQL with Subscriptions
**Approach:** Replace REST API with GraphQL
**Pros:** Efficient queries, built-in subscriptions
**Cons:** Large refactor, learning curve, complexity
**Decision:** Rejected - WebSocket simpler for chat use case

### 3. gRPC with Streaming
**Approach:** Use gRPC bidirectional streaming
**Pros:** Efficient binary protocol, strong typing
**Cons:** Browser support requires grpc-web proxy, complexity
**Decision:** Rejected - WebSocket more standard for web apps

### 4. Server-Sent Events (SSE)
**Approach:** Use SSE for server-to-client, HTTP for client-to-server
**Pros:** Simpler than WebSocket, automatic reconnection
**Cons:** Unidirectional, still need HTTP for client messages
**Decision:** Rejected - WebSocket provides full duplex

## References & Best Practices

### Industry Examples

**Slack:**
- [Slack Real-time Messaging API](https://api.slack.com/rtm)
- Uses WebSocket for all real-time data
- HTTP API for file uploads, search, admin

**Discord:**

- WebSocket gateway handles all events
- Binary encoding option for efficiency
- Heartbeat mechanism for connection health

**Mattermost:**
- [Mattermost WebSocket API](https://docs.mattermost.com/integrate/reference/websocket-api.html)
- WebSocket for real-time, HTTP for operations
- State reconciliation on reconnect

### Slack's Token Validation

Slack caches token validation results:
- First request: Validate with auth server
- Subsequent requests: Use cached result (5-15 min TTL)
- Invalidation: On logout, password change, revocation
- Result: 99%+ cache hit rate in production

### Best Practices

1. **Connection Management**
   - Heartbeat every 30s to detect dead connections
   - Client-side reconnection with exponential backoff
   - Server-side connection limits per user (prevent abuse)

2. **State Management**
   - Server is source of truth
   - Client maintains optimistic UI state
   - Reconcile on reconnection
   - Use message sequence numbers for ordering

3. **Error Handling**
   - Graceful degradation (fall back to HTTP if WebSocket fails)
   - Clear error messages to user
   - Automatic retry with backoff
   - Log errors for monitoring

4. **Security**
   - Authenticate WebSocket on connect (token in URL param or first message)
   - Validate all incoming messages (don't trust client)
   - Rate limit per connection
   - Encrypt all traffic (WSS, not WS)

5. **Monitoring**
   - Track connection count, churn rate
   - Monitor message latency (time from send to ack)
   - Alert on delivery failures
   - Track cache hit rates

## Conclusion

The current architecture's over-reliance on HTTP API calls creates a scalability bottleneck, particularly with repeated token validation to TitaniumVault.

**Short-term (1-2 weeks):** Implement token caching to reduce TitaniumVault calls by 90%+

**Medium-term (4-6 weeks):** Migrate to WebSocket-first architecture, eliminating HTTP calls for channel operations

**Long-term (3-6 months):** Full real-time platform with instant updates, superior UX, and efficient resource usage

This aligns OpenChat with industry standards (Slack, Discord, Mattermost) and enables scaling to millions of users efficiently.
